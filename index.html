三个引擎、两套 4-bit 权重、四套配置，同一台机器、同样的请求。Halogen 用自家 v2 权重最快、最省内存；Strata 用的 UD-Q4_K_XL 权重 PPL 低约 2%；在同一份 UD-Q4_K_XL 权重上，Gufo 和 Halogen 速度接近，都明显快于 Strata。准确率方面，Halogen v2 和 Gufo + UD 四项全部持平。GSM8K 上 Halogen v2 默认低约 8 分，是因为 Halogen 默认不让回答停在 Markdown 标题行；关掉这个设置后为 96.1% 对 96.0%。

准确率评测Accuracy evals

Halogen v2 和 Gufo + UD 在四项任务上全部持平。HumanEval、IFEval、MMLU-Pro 在默认设置下差距就在误差范围内。GSM8K 默认差约 8 个百分点（87.7% 对 96.0%），原因是 Halogen 的一个默认设置，不是模型算错了题；关掉这个设置后为 96.1% 对 96.0%。

Halogen v2 and Gufo + UD tie on all four tasks. HumanEval, IFEval and MMLU-Pro are within the error bars on default settings. GSM8K differs by about 8 points by default (87.7% vs 96.0%), caused by a Halogen default setting rather than the model getting the maths wrong; with that setting off it is 96.1% vs 96.0%.

GSM8K 为什么低Why GSM8K is lower

Halogen 默认开启 answer guard：回答的最后一行如果是 Markdown 标题（以 # 开头），它不让回答结束。GSM8K 的提示要求最后一行写成 #### 数字，正好被当成标题。模型想停却停不下，只能接着重复 #### 18、补一段 JSON，或在数字后面不停补 0，直到 1,024 token 上限。评分取最后一个 ####，被截断的回答常被判错，比如答对的 540 被截成 #### 54。只关掉这个设置重跑 GSM8K，Halogen v2 从 87.7% 升到 96.1%，触及上限的题从 444 道降到 21 道；和 Gufo + UD 的 96.0% 差距在误差范围内（逐题对比：只有 Halogen 答对 16 题，只有 Gufo 答对 15 题）。已报告给 Halogen：halogen-flash-server#259。

Halogen turns on an answer guard by default: if the last line of a reply is a Markdown heading (starting with #), it won't let the reply end. The GSM8K prompt asks for a final line of #### number, which reads as a heading. The model tries to stop and can't, so it repeats #### 18, appends a JSON block, or keeps adding zeros to the number until the 1,024-token limit. Scoring takes the last ####, so truncated replies often score wrong; a correct 540 cut to #### 54, for example. Rerunning GSM8K with only that setting off lifts Halogen v2 from 87.7% to 96.1%, and answers hitting the limit drop from 444 to 21; the remaining gap to Gufo + UD (96.0%) is within the error bars (question by question, 16 right only on Halogen, 15 right only on Gufo). Reported upstream as halogen-flash-server#259.

  • 只改了在哪里停：同一道题，关掉 answer guard 后的回答和默认设置下回答的开头一字不差（1,319 题里 1,316 题），只是在答案行就停住了。和默认相比多答对 111 题，只少答对 1 题。Only where it stops changes: on the same question, the guard-off reply matches the start of the default reply word for word (1,316 of 1,319), it just stops on the answer line. Against the default run it gets 111 more right and 1 fewer.

With only the answer guard off, all six end normally.
  • 逐项排除：在原来循环的 24 道题上，关掉 MTP 草稿、关掉提示查找草稿，结果和默认完全一样（24 题全部截断）；只关 answer guard，24 题全部停在答案行。另一个开关 end-of-turn guard 保持开启也不影响。One change at a time: on 24 questions that looped, turning off MTP drafting or prompt-lookup drafting changed nothing (all 24 still truncated); turning off only the answer guard made all 24 stop on the answer line. The separate end-of-turn guard can stay on.
  • 不是权重的问题：Gufo 的 1,294 个正常结束的回答全部停在 #### 行，Halogen v2 一个都没有。Halogen 跑和 Gufo 同一份 UD-Q4_K_XL 权重（Halogen + UD）时也一样，GSM8K 只有 84.1%。Not the weights: all 1,294 of Gufo's normally ended replies stop on the #### line; none of Halogen v2's do. Halogen on the same UD-Q4_K_XL weights as Gufo (Halogen + UD) behaves the same and scores 84.1% on GSM8K.
  • 其他三项不受影响：它们的回答很少以标题行结尾，两套配置的截断回答里没有一例是标题行循环。The other three tasks are unaffected: their replies rarely end on a heading, and none of the truncated replies on either setup is a heading loop.
  • 在评测端也能部分补救：遇到第一行答案就截断，Halogen v2 能回到 91.3%。但有 57 道题是在数字后面一直补 0（如 70000000…），评测端不知道该在哪一位截断，救不回来。在服务端关掉 answer guard 才能完全解决。The eval side can recover part of it: cutting each reply at its first answer line brings Halogen v2 back to 91.3%. But 57 replies keep adding zeros to the number (such as 70000000…), and the eval side can't tell where to cut them. Only turning the answer guard off on the server fixes it fully.
  • MMLU-Pro：两套都有约 14% 的题没提取到答案（Halogen v2 139 题，Gufo + UD 141 题），这压低了两边的分数。MMLU-Pro: about 14% of questions yielded no extractable answer on both setups (Halogen v2 139, Gufo + UD 141), which lowers both scores.

质量：WikiText-2 困惑度（PPL）Quality: WikiText-2 perplexity

Strata has no perplexity tool and returns no prompt-token probabilities; Gufo's NLL tool is not in its released container. Engine-specific numeric error was therefore not measured separately.

“A → B”是空闲时到测试结束时。Gufo 默认的提示缓存会随使用增长（最多空闲内存的一半、不超过 32 GiB）。Halogen 的“系统显示可用”偏高，因为锁定的权重被算成可释放缓存，这里按启动前可用内存减去引擎合计。

"A → B" is idle to end of testing. Gufo's default prompt cache grows with use (up to half of free RAM, at most 32 GiB). Halogen's MemAvailable is overstated because pinned weights count as reclaimable cache, so its figure is available memory before start minus the engine total.

功耗、温度与稳定性Power, temperature and stability

  • 四套功耗几乎一样，所以每个 token 的耗电和速度成反比：Halogen v2 最省电，Strata 最费电。All four draw about the same power, so energy per token is the inverse of speed: Halogen v2 uses the least, Strata the most.
  • Strata 卡死一次。131K 提示第一次读到第 90,112 个 token 时显卡 60 秒没有进展，Strata 自动重启引擎，重试成功。当时系统可用内存只有约 2 GiB。Strata stalled once. On the first 131K attempt the GPU made no progress for 60 s at token 90,112; Strata restarted its engine and the retry succeeded. Free memory was about 2 GiB at the time.

准确率评测Accuracy evals

HumanEval、IFEval（lm_eval 官方评分）、GSM8K 和 MMLU-Pro（固定种子分层抽样），四套配置题目相同；关闭思考，温度 0，每次一个请求。设置和上面的速度测试不同：Gufo 用 2 个会话、32,768 上下文，Strata 用 128K 上下文，Halogen 用默认启动命令（Halogen + UD 因内存不足自动把 KV 池降到 262,144）。评测题都很短，预计不影响答案，但没有单独验证；这组运行的速度也不能和上面的速度数据直接比。“Halogen v2（关闭 answer guard）”只重跑了 GSM8K，启动命令只多加了 -e HALOGEN_ANSWER_GUARD=0。

HumanEval, IFEval (lm_eval's official scoring), GSM8K and MMLU-Pro (stratified sample, fixed seed), with identical questions on all setups; thinking off, temperature 0, one request at a time. Settings differ from the speed tests above: Gufo uses 2 sessions and a 32,768 context, Strata a 128K context, Halogen its default launch command (Halogen + UD lowered its KV pool to 262,144 automatically for lack of memory). The questions are short, so answers shouldn't be affected, but this wasn't verified separately, and speeds from these runs aren't directly comparable to the figures above. "Halogen v2 (answer guard off)" reran GSM8K only, with -e HALOGEN_ANSWER_GUARD=0 as the only change to the launch command.

速度、内存与 PPLSpeed, memory and perplexity

llm-probe.sh 给每套配置发完全相同的请求：3 个短提示各生成 256 token；8K、32K、131K 提示各生成 128 token；同一个 30,023 token 长提示；每 0.5 秒记录 GTT、可用内存、芯片封装功耗和 GPU 温度。标准测试是 strata bench run（standard-v1），用 replay-bench.py 原样发给其他配置。PPL 用 Halogen 的 ppl 工具在 WikiText-2 测试集（wiki.test.raw，297,192 token）上计算，并做逐 token 配对检验。电源模式“平衡”。

llm-probe.sh sends identical requests to every setup: 3 short prompts with 256 tokens out; 8K, 32K and 131K prompts with 128 tokens out; one 30,023-token prompt; GTT, MemAvailable, package power and GPU temperature sampled every 0.5 s. The standard benchmark is strata bench run (standard-v1), replayed unchanged with replay-bench.py. Perplexity is Halogen's ppl tool on the WikiText-2 test set (wiki.test.raw, 297,192 tokens), with a per-token paired test. Power profile: balanced.
